# Coding Conventions

## Rust Style

- Use Rust 2021 idioms and keep code compatible with the workspace manifests.
- Format with `cargo fmt`.
- Prefer `Result` or diagnostic emission for user-facing errors. Avoid panics on malformed source or grammar input unless the invariant is internal and already validated.
- Keep public APIs small and crate-local helpers private where practical.
- Use explicit names for compiler concepts: `grammar`, `rule`, `lookahead`, `scope`, `span`, `operand`, `block`, `interval`.
- Preserve existing module ownership. Parser algorithms belong in `lexion_lib`; grammar-file parsing belongs in `lexion_parsers`; language semantics and code generation belong in `lexion_lang`.

## Error And Diagnostic Style

- Diagnostics should include the original `NamedSource` and the narrowest correct `SourceSpan`.
- Prefer actionable messages: state what was expected, what was found, and the relevant identifier/operator/type.
- Use warnings for legal but suspicious code, such as shadowing.
- Do not replace structured diagnostics with `println!` output in normal compiler paths.
- Keep debug output behind dump flags where possible.

## Parser And Grammar Style

- Keep grammar rules explicit and deterministic.
- Do not rely on parse table conflict ordering to resolve ambiguity unless a task explicitly introduces precedence or conflict resolution.
- Treat EOF and epsilon as first-class grammar cases.
- Preserve terminal token ordering when it affects tokenizer precedence.
- For new parser algorithms or table behavior, add focused tests with simple grammars before wiring changes into `lexion_lang`.
- For grammar updates, update both grammar source and generated grammar data together when generation is part of the workflow.

## AST And Visitor Style

- Wrap source-backed values in `Sourced<T>` when spans are needed for diagnostics.
- Add new AST nodes to both immutable and mutable visitor paths.
- Keep visitor traversal order explicit when compiler stages depend on preorder or postorder behavior.
- Write inferred type indexes back to expressions in the type checker.

## Symbol And Type Style

- Use `TypeCollection` for type storage and comparison rather than ad hoc string comparisons.
- Canonicalize and dereference types where local patterns already do so.
- Insert symbols through `SymbolTableGraph` helpers so sorting and duplicate checks remain consistent.
- Keep scope entry and exit symmetric in traversal code.
- Add temporary symbols generated by IR code with a type and span when available.

## IR And Backend Style

- Keep TAC generation independent from x86-specific details where possible.
- Represent control flow with CFG edges, not only labels and jump instructions.
- Keep liveness data recomputable from instructions instead of manually maintaining it across edits.
- Reset allocator state per function.
- Do not hard-code calling convention assumptions outside the x86 calling convention modules.

## Tests And Snapshots

- Use focused unit tests for parser algorithms and compiler-stage helpers.
- Use fixture tests for language behavior.
- Use `insta` snapshots for stable diagnostic or parse table output.
- Canonicalize graph/table output before snapshotting when node numbering can vary.
- Do not leave newly relevant tests ignored. If an ignored test remains ignored, the reason must still be true.

## Formatting And Tooling

- Before committing Rust changes, run `cargo fmt --all`.
- Prefer `cargo test -p <crate>` for focused validation and `cargo test` for cross-crate parser/compiler changes.
- Do not commit `target/` artifacts.
- Do not commit dump output unless explicitly requested.
